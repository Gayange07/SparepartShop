# Embed customer returns inside POS sale transaction

Customer returns should ship as a POS-embedded flow that **extends the existing `POST /api/sales` transaction** rather than a separate endpoint, because the user's "same bill" rule and the atomicity requirement (stock-in, stock-out, return rows, sale row all commit or none) rule out two-endpoint designs. The approved v3 blueprint has **no customer-return UX** ([plan.md §1](../research_notes/Customer%20returns%20exchange%20flow/plan.md)), so this is net-new; however the `returns` table ([`server/src/db/schema/returns.ts`](../server/src/db/schema/returns.ts)) is **already fully shaped** for customer returns with `partyType` and `saleId` columns, and the supplier-return handler at [`server/src/suppliers/routes.ts` lines 197-232](../server/src/suppliers/routes.ts) is a near-perfect template — only `qtyDelta` sign and `partyType` flip. The injection model mirrors the pre-order advance pattern (`advanceDeductedCents` in [`shared/src/billing.ts` lines 91-92](../shared/src/billing.ts)): the client sends a `returns: SaleReturnLineInput[]` array on `SaleInput`, the server authoritatively re-prices each line from `sale_items.unitPriceCents`, and `computeBillTotals` subtracts `returnCreditCents` from `dueCents`. Pure refunds (empty cart, returns only) use the same handler but skip the `sales` insert and respond with `refundOutCents` only. No new schema migrations are needed for the MVP ([plan.md §7](../research_notes/Customer%20returns%20exchange%20flow/plan.md)).

## The v3 blueprint ships supplier returns but no customer-return UX

The approved v3 prototype at `docs/blueprint/SpareParts-ERP-v3.html` implements **only supplier returns**, with `supReturns:[]` declared at line 333 and a single `seq('RET')` call at line 928 inside the supplier-return save ([plan.md §1](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). A grep for `custReturn|customerReturn|cust_return|exchange|refund|return.*customer` across the HTML returns zero hits for any customer-return handler, modal, button, or data path. CLAUDE.md lists `RET-` as a sequence prefix without scoping it to supplier returns, and the real `returns` table (migration [`server/drizzle/0000_minor_viper.sql` lines 316-339](../server/drizzle/0000_minor_viper.sql)) enforces `return_no NOT NULL UNIQUE` across all parties. The implementation therefore **reuses a single `RET-00001` sequence for both supplier and customer returns** — the `nextSeq("RET", returns, undefined, tx)` call does not partition by `partyType`, so customer RET-00042 slots directly after supplier RET-00041 ([plan.md §1](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). This matches CLAUDE.md's prefix list and avoids a schema change. Because the blueprint is silent on UX, this is net-new design — but it must still match the Workshop theme and the existing `Sheet` / `ServiceChargeSheet` structural pattern.

## The returns table and all enums are already provisioned

The `returns` table in [`server/src/db/schema/returns.ts`](../server/src/db/schema/returns.ts) carries every column the feature needs: `id, returnNo (unique), partyType ("supplier"|"customer"), supplierId, customerId, grnId, saleId, partId, grade, qty, amountCents, reason, createdBy, createdAt` ([plan.md §2](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). The `stockMovements.reason` enum at [`server/src/db/schema/stock-movements.ts` line 10](../server/src/db/schema/stock-movements.ts) already accepts `"return"`, and the `activityLog.action` enum at [`server/src/db/schema/activity-log.ts` line 15](../server/src/db/schema/activity-log.ts) already accepts `"return"` — both without migration. The supplier-return reference implementation at [`server/src/suppliers/routes.ts` lines 197-232](../server/src/suppliers/routes.ts) is the canonical template: it validates `SupplierReturnInput`, re-reads `partGrades` inside a transaction, **decrements** stock, inserts a `returns` row, inserts a `stockMovements` row with `qtyDelta: -input.qty, reason: "return", refType: "return", refId: row.id`, and calls `logActivity({ action: "return", entityType: "supplier" })`. The customer-return handler mirrors this exactly but **inverts the sign**: `qtyDelta: +input.qty` (stock back in), `partGrades.qty + input.qty`, `partyType: "customer"`, with `saleId` and `customerId` populated from the referenced sale. The schema has no `sale_item_id` FK, so "already returned qty" is computed at request time from `returns.where(saleId=X, partId=P, grade=G).sum(qty)`; this works because the POS cart dedupes by `(partId, grade)` at [`web/src/lib/cart.ts` line 15](../web/src/lib/cart.ts), making the `(saleId, partId, grade)` tuple effectively unique in `sale_items` ([plan.md §2](../research_notes/Customer%20returns%20exchange%20flow/plan.md)).

## The exact server route is extended POST /api/sales, not a new endpoint

Three injection options were evaluated ([plan.md §4](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). **Option A — embed `returns[]` in `SaleInput`** wins because it keeps return rows, stock-back, sale row, and stock-out inside **one atomic transaction** and produces **one receipt**, directly matching the user's "same bill" rule. Option B (separate `POST /api/returns` → then `POST /api/sales` with `creditAppliedCents`) fails the atomicity test — stock can go back in while the sale fails. Option C (new column + inner call) solves nothing Option A doesn't already solve. The exact Zod schema addition in [`shared/src/billing.ts`](../shared/src/billing.ts):

```ts
export const SaleReturnLineInput = z.object({
  saleId: z.number().int().positive(),
  partId: z.number().int().positive(),
  grade: GradeKey,
  qty: z.number().int().positive(),
  reason: z.string().default(""),
});
export type SaleReturnLineInput = z.infer<typeof SaleReturnLineInput>;
```

`SaleInput` gains `returns: z.array(SaleReturnLineInput).default([])`, and the existing `.refine((v) => v.lines.length > 0 || v.services.length > 0)` must be relaxed to accept `v.returns.length > 0` alone — otherwise pure refunds are rejected at validation ([plan.md §4](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). The optional `ownerAuthPassword?: string` field is already on `SaleInput` (used by void), and an optional `applyRefundToCredit?: boolean` flag controls cash-vs-credit refund routing. The server **never** trusts client-sent refund amounts — for each return line, the handler looks up `sale_items.where(saleId=..., partId=..., grade=...).unitPriceCents` and computes `refundCents = unitPriceCents × qty`, then enforces five guards per line: sale exists, `sale.status !== "voided"` ([`sales.ts` line 25](../server/src/db/schema/sales.ts); void handler at [`server/src/sales/routes.ts` lines 229-273](../server/src/sales/routes.ts)), sale_item exists, `qty ≤ saleItem.qty − alreadyReturnedQty`, and the age gate (next section).

## Return credit flows through computeBillTotals and signed changeCents

`computeBillTotals` in [`shared/src/billing.ts`](../shared/src/billing.ts) gains an optional `returnCreditCents?: number` parameter, parallel to the existing `advanceDeductedCents` ([plan.md §4](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). The output formula becomes `dueCents = Math.max(0, totalCents − advanceDeductedCents − returnCreditCents)` plus a new `refundOutCents = Math.max(0, (advanceDeductedCents + returnCreditCents) − totalCents)`. This yields the three UX states cleanly: `due > 0` labels "To collect"; `due === 0` labels "Settled"; `due < 0` (represented as `refundOutCents > 0`) labels "**Cash to refund**" in red, hides the payment selector, and shows a read-only summary. The pure-refund case falls out of the same math: cart empty + returns present → `totalCents = 0`, `refundOutCents = Σ refundCents`, no sale row inserted. For the mixed case (new items + returns, with net cash out to customer), the plan **reuses `sales.changeCents` as a signed int** rather than add a column: positive means change given to the customer, negative means cash paid out as refund ([plan.md §5](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). SQLite's INTEGER is signed natively; only the receipt printer needs an update to render the sign.

Refund routing has two destinations. **Cash refund (default)** writes a signed `changeCents` on the sales row (mixed case) or responds with `refundOutCents` for the handler to settle at the drawer (pure case). **Customer-credit refund** — available only when the referenced sale was a credit sale or when the current customer carries an outstanding balance — inserts a `payments` row `{paymentNo: nextSeq("RCP", payments, eq(payments.type, "customer_credit")), type: "customer_credit", partyId: customerId, amountCents: refundOutCents, method: "return_credit", note: "From returns RET-..."}` in the same transaction. This correctly reduces `customerBalanceCents` via the formula at [`server/src/customers/balance.ts` lines 7-18](../server/src/customers/balance.ts): `balance = Σ(credit_sale.totalCents − amountPaidCents) − Σ(customer_credit payments)` ([plan.md §5](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). Whether the `payments.method` enum needs `"return_credit"` added depends on current schema state — if method is open text (likely), no migration is needed; otherwise a one-line enum extension generates a new drizzle migration.

## The age gate reuses the void endpoint's argon2 flow

CLAUDE.md requires owner authorization for voids and credit sales; this feature extends the same gate to **returns of bills older than 2 days** ([plan.md §3](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). The server computes `ageMs = Date.now() − new Date(sale.createdAt).getTime()`. If `ageMs > 2 * 24 * 3600 * 1000` and the caller is not the owner, the handler requires `input.ownerAuthPassword` and verifies it with `argon2.verify(settingsRow.ownerAuthPasswordHash, input.ownerAuthPassword)` — the exact pattern already in use at [`server/src/sales/routes.ts` lines 240-246](../server/src/sales/routes.ts) for void. On failure: `logActivity({ action: "owner_auth_failed", details: { context: "customer_return", saleId } })` and respond `401 { error: "Wrong authorization password" }`. The route uses `preHandler: app.requireAuth` rather than `requireAllPermissions(["stock", "cost"])` because customer returns don't touch cost prices and the discriminator is sale age, not a staff capability — a shopkeeper is allowed within 2 days without any password, and blocked beyond 2 days without owner override ([plan.md §3](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). This matches the user's stated policy exactly.

## The POS sheet is a two-stage flow mounted on the Bill card

The UX ([plan.md §8](../research_notes/Customer%20returns%20exchange%20flow/plan.md)) adds an `<Button variant="outline">` labeled **"Exchange or return items"** with the `LuRotateCcw` icon on the right-sidebar Bill card in [`web/src/pages/pos.tsx`](../web/src/pages/pos.tsx), mirrored into the mobile overflow near "Add service charge". The sheet reuses the `Sheet` primitive at [`web/src/components/ui/sheet.tsx`](../web/src/components/ui/sheet.tsx) — bottom-sheet on phone, dialog on desktop — and runs a two-stage state machine. **Stage 1 "find"** uses a debounced `Input` wired to the existing `GET /api/sales?q=` endpoint at [`server/src/sales/routes.ts` lines 185-210](../server/src/sales/routes.ts) which already filters by invoice/customer/vehicle; results render as scrollable rows with `INV-xxxxx`, customer name, date (Asia/Colombo), total, status. Voided bills show a "VOIDED" badge and are disabled; bills older than 2 days tint with `bg-destructive-soft` and show a `LuShieldAlert` chip "Needs owner approval". **Stage 2 "pick"** calls `GET /api/sales/:id` (which should be augmented with `alreadyReturnedQty` per sale_item to save a round-trip), renders each item as a row with checkbox, qty stepper (reusing the three-button pattern at [`web/src/pages/pos.tsx` lines 250-254](../web/src/pages/pos.tsx)), per-row refund in `font-cond tabular`, and a bottom-footer "Reason (optional)" `Input`. For >2-day bills, an owner-auth `Input type="password"` appears with the error-aware styling from the credit-sale sheet at [`web/src/pages/pos.tsx` lines 345-355](../web/src/pages/pos.tsx).

Applied returns surface in the main POS as **negative-valued lines pinned to the top of the cart**, each labeled `RET source: INV-xxxxx — <part name>` with a red minus sign and `−Rs. X,XXX.XX` in `font-cond tabular`. They are **not stored in `useCart`** to keep that primitive simple; a new sibling hook `useReturns()` in [`web/src/lib/returns-cart.ts`](../web/src/lib/returns-cart.ts) tracks the queued returns and exposes `totalRefundCents`. The totals block gains one row between "Discount" and "Round off": `Return credit  − Rs. X,XXX.XX`. The "Total" row relabels dynamically — "To collect" when `due > 0`, "Cash to refund" (red `#B23E2C`) when `due < 0` — and the payment selector plus "Cash received" fields collapse into a single read-only "Cash to refund" summary when the net is negative ([plan.md §8](../research_notes/Customer%20returns%20exchange%20flow/plan.md)). Red is used only on the >2-day row tint and the "Cash to refund" line, matching CLAUDE.md's "red for low stock / owed only" rule.

## The file-by-file execution plan commits in four steps

Four commits deliver the feature, matching CLAUDE.md's "commit after each working step" rule ([plan.md §9](../research_notes/Customer%20returns%20exchange%20flow/plan.md)).

**Commit 1 — shared.** Edit [`shared/src/billing.ts`](../shared/src/billing.ts): add the `SaleReturnLineInput` Zod object quoted above, extend `SaleInput` with `returns: z.array(SaleReturnLineInput).default([])`, relax the `.refine(...)` to accept `v.returns.length > 0`, and extend `computeBillTotals` to accept `returnCreditCents?: number` and return `refundOutCents`. Create [`shared/src/billing.test.ts`](../shared/src/billing.test.ts) with four Vitest cases: `computeBillTotals applies return credit before due`, `return credit greater than total surfaces as refundOutCents`, `return credit + advance + total 0 edge case`, and Zod `SaleInput accepts returns array alone (no lines/services)`.

**Commit 2 — server.** Edit `POST /api/sales` in [`server/src/sales/routes.ts`](../server/src/sales/routes.ts): before the main transaction, loop `input.returns`, fetch each `sales` row (reject voided), fetch each `sale_items` row, compute `alreadyReturned` and reject overages, compute `refundCents` from `unitPriceCents × qty`, sum into `totalReturnCreditCents`. Apply the age gate with argon2 verify per older-than-2-days sale. Call `computeBillTotals(..., { returnCreditCents: totalReturnCreditCents })`. Inside the existing `db.transaction((tx) => { ... })`: for each return line call `nextSeq("RET", returns, undefined, tx)`, insert a `returns` row with `partyType: "customer"`, increment `partGrades.qty`, insert a `stockMovements` row with `qtyDelta: +qty, reason: "return"`. If `refundOutCents > 0` and `applyRefundToCredit`, insert a `payments` row of type `customer_credit`; else set `changeCents = -refundOutCents` on the sales row. For the pure-refund path (`lines.length === 0 && services.length === 0 && returns.length > 0`), skip the sales insert entirely and respond `{ returns, refundOutCents, creditAppliedCents }`. Add a `logActivity({ action: "return", entityType: "sale", details: { saleId, returnNos, refundCents } })` call after commit. Augment `GET /api/sales/:id` to include `alreadyReturnedQty` per sale_item. Add seven Vitest cases in [`server/src/sales/routes.test.ts`](../server/src/sales/routes.test.ts): returns-in-SaleInput happy path (stock increments, return rows inserted, totals net), mixed bill (due = total − credit, negative becomes refundOutCents), pure refund (no sales row), shopkeeper blocked >2 days without password, shopkeeper success with password + 401 on wrong password with `owner_auth_failed` log, over-returning rejected 400, voided-sale return rejected 400, customer_credit payment created when `applyRefundToCredit` set.

**Commit 3 — web core.** Create [`web/src/lib/returns-cart.ts`](../web/src/lib/returns-cart.ts) exporting `QueuedReturn` type and `useReturns()` hook with `{ returns, add, remove, clear, totalRefundCents }`. Create [`web/src/pages/pos/return-sheet.tsx`](../web/src/pages/pos/return-sheet.tsx) implementing the two-stage sheet with props `{ open, onClose, onApply(returns, ownerAuthPassword?) }`. Edit [`web/src/pages/pos.tsx`](../web/src/pages/pos.tsx) to add the `useReturns()` call, the "Exchange or return items" button, the queued-return rows at the top of the cart list, the `returnCreditCents` plumbing into the local `computeBillTotals`, the dynamic "Total" / "Cash to refund" relabel, the `buildPayload()` additions (`returns: [...], ownerAuthPassword: ...`), and `resetAll` cleanup. Mount `<ReturnSheet>` and lift the owner password up on `onApply`.

**Commit 4 — web polish.** Add red `bg-destructive-soft` tint for >2-day result rows, voided-row disable with "VOIDED" badge, the `LuRotateCcw` and `LuShieldAlert` icons, `font-cond tabular` on the refund amount, and a Workshop-theme consistency pass against the colors `#B23E2C` (refund-out) and `#F3F5F4` (background). ## Conclusion

The decisive insight is that the schema and enums are **already in place** — this feature is a transaction-shape change, not a data-model change. The real engineering risk is **state leakage across the three concurrent concepts** (cart, services, queued returns) in the POS page: the plan's choice to keep `useReturns()` as a sibling hook (not inside `useCart`) is correct because it keeps rollback semantics clean on `resetAll` and lets the live-preview `computeBillTotals` stay a pure function of three independent inputs. The second subtle insight is that **reusing `changeCents` as a signed int** avoids a schema migration but requires receipt-printer awareness — flag this for the desktop Electron receipt renderer when that work lands in step 11-13 of the project build plan.

One open policy question remains for the owner: whether the refund should be the pre-discount `unitPriceCents × qty` (current recommendation, simplest) or the proportional post-discount paid value `unitPriceCents × qty × (totalCents / subtotalCents)`. The notes default to the simpler model; if the owner later wants exact-paid pro-rata, the formula sits entirely inside `computeBillTotals` and is a localized change. The receipt-reprint-for-returns path (printing a standalone `RET-xxxxx` receipt) is out of scope for this feature and should be a follow-up tied to the receipt generator work.
